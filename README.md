# 换热站隔热垫试装验收

清浦热力运行部试装验收组。清浦热力直管 36 座片区换热站，本轮在每座站预先选定一个稳定负荷窗口，记录同站原垫和试装垫工况匹配的平均热损。计量班交台账，设备工程师运行验收，技术值班长复核，采购组据此安排下一批试装。

一行对应一座换热站的一组原垫和试装垫读数。CSV 记录登记方案、配对号、站号、共同负荷窗口起点（北京时间，YYYY-MM-DD HH:MM）及两次平均热损（kW）。 验收组查看有效配对数、平均热损差、单侧 95% 置信上界和锁定的 0.50 kW 界值。报告保留站点、原始读数与配对差，满足验收条件后供技术值班长审批并分发给设备采购组。

- 计量班原先从两份 Excel 工况表抄数，配对号和换热站号容易错位，同站补测还会被误计为独立样本。
- 工程师原先凭热损均值与容许增量对比，漏掉了小样本的不确定性和单侧临界值。
- 技术值班长复核邮件附件时要追问界值何时批准，采购组收过缺少原始配对证据的版本。

## 六个业务模块

1. 试装验收总览
2. 配对测量台账
3. 非劣效检验
4. 站点差值明细
5. 试装验收复核
6. 验收报告分发

2. 11 月 12 日 08:00，计量班记录 HX-01 的 PAD-001，原垫 8.12 kW，试装垫 7.94 kW。
3. 11 月 23 日 14:00 完成 HX-36；11 月 24 日 08:40 导入 pad_paired_heat_loss_20261123.csv，共 36 站、36 组配对。
4. 11 月 24 日 08:45，计量班一并导入站点与批次对应表，36 座站分属 CAL-01 至 CAL-06 六个校准批次。
5. 11 月 24 日 09:00，设备工程师按 12 站门槛运行，平均差 0.0675 kW，单侧 95% 上界约 0.1493 kW；撤回任意零到四批后最高上界 0.2578 kW（撤回 CAL-01、CAL-03、CAL-04、CAL-05），仍低于 0.50 kW 界值。

## 算法与复核

方案 HR-PAD-20261110-V1 于 2026-11-10 09:00（北京时间）登记，锁定界值 0.50 kW、单侧 95% 置信水平和至少 12 个有效站点。按试装垫减原垫形成站点配对差，以 n−1 自由度的 Student t 分位数计算平均差的单侧上界。各站点配对差需独立，小样本时差值应近似正态。复核门槛可提高，判定使用未舍入数值。

同一校准批次的仪表可能一起失准，因此验收同时做撤回敏感性复核：对撤回 0 至 4 个校准批次的全部组合，各按原口径（未舍入）重算单侧 95% 置信上界，取其中最高者作为本批最高上界，并记下对应的撤回批次。任一组合剩余站点不足复核门槛、上界算不出（自由度不足或配对差标准误为零）或上界达到/超过 0.50 kW 界值，即暂缓验收并阻断批准和分发。组合按批次整批撤回、逐一精确枚举：60 批时为 523686 个组合，约一秒算完；最多支持 100 批（约 409 万个组合，数秒内完成），超过上限直接退回要求合并批次或拆分台账。

验收时一次导入测量记录与站点—批次对应表，每座换热站须恰好归属一个校准批次；少配、多配或站点重复都在导入时退回。原始数据（含批次归属）按规范化内容的 SHA-256 去重。更正批次归属另开数据版本；分析任务在受理时即固化当时的测量记录与批次归属，worker 中断后重新领取仍按受理时的口径计算，不受期间新版本影响。

方案不符、登记时间之前或同分钟采集、窗口无效、配对号或站点重复、热损无效时退回台账。有效配对不足、配对差标准误为零、置信上界达到或超过登记界值，或任一撤回组合触发暂缓时，阻断批准和分发。 复核问题为「本批有效配对是否达到复核门槛，且单侧 95% 置信上界是否严格低于试装前登记的 0.50 kW 界值？」。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `protocol_id` | 登记方案编号 | str |
| `pair_id` | 配对编号 | str |
| `station_id` | 换热站编号 | str |
| `window_start` | 测量窗口起点（北京时间） | str |
| `baseline_loss_kw` | 原垫平均热损（kW） | float |
| `trial_loss_kw` | 试装垫平均热损（kW） | float |

站点—批次对应表另用一份 CSV：

| 字段 | 含义 | 类型 |
|---|---|---|
| `station_id` | 换热站编号 | str |
| `calibration_batch` | 校准批次编号 | str |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18292`
- API 文档 `http://127.0.0.1:19292/docs`
- 数据库端口 `17792`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、PostgreSQL 16 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。`backend/src/models/migrate.py` 在启动时为既有的数据库卷补上新增的空列，重复执行不会重复添加。

业务算法的纯标准库单元测试位于 `backend/tests`：

```sh
cd backend && python -m unittest discover -s tests -t .
```

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
